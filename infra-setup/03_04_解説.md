# 03 / 04 の解説（ステップごとに何をしているか）

`infra-setup/03_tljh_create_vm.sh` と `04_tljh_provision.sh` を読むための補助資料。
Linux / GCP の用語に馴染みがなくても追えるように、各ステップの「何を」「なぜ」を書く。

一言でいうと **03 = GCP 側の箱（VM・IP・ファイアウォール）を用意する、04 = 箱の中に JupyterHub を入れて上限と接続先を設定する**。

```
手元PC ── 03 を実行 ──▶ GCP に VM fx-tljh ができる
                            │ 初回起動時に startup-script として
                            ▼
                        VM 内で 04 が root で自動実行される（5〜10分）
                            │
                            ▼
                        http://<静的IP> で JupyterHub にログインできる
```

**04 は手で実行しない。** 03 が中身をメタデータとして VM に渡し、GCE の仕組みで初回起動時に自動実行される。

---

## 03_tljh_create_vm.sh（手元で実行・約1分）

### 1. config.sh を読み込む
プロジェクト `fx-itnern`、ゾーン `asia-northeast1-b`（東京）など全スクリプト共通の値。
app/DB VM と同じゾーンに置くのは、VM 間通信を内部ネットワークで往復 0.1〜0.5ms にするため。

### 2. app/DB VM の内部 IP を取得
`gcloud compute instances describe ... networkIP` で `fx-trade-api-ssd` の **内部 IP**（10.x.x.x）を取る。
参加者のノートブックはこの IP 経由で API（FastAPI, port 8000）を叩く。外部 IP ではなく内部 IP を使うのは速くて無料だから。

### 3. ファイアウォールルール `allow-tljh-http` を作る
GCP は既定で外からの通信を全部遮断している。参加者のブラウザが `http://<IP>` にアクセスできるよう、
**タグ `tljh` が付いた VM の tcp:80 だけ**を開ける。既にルールがあればスキップ（何度実行しても安全 = 冪等）。

### 4. 静的外部 IP `fx-tljh-ip` を予約する
GCE の VM は既定では起動のたびに外部 IP が変わる（エフェメラル IP）。
静的 IP を予約して VM に固定すると、**停止→起動やマシンタイプ変更をしても URL が変わらない**ので、参加者に事前に URL を配れる。
既に予約済みならスキップ。リージョンはゾーン名から末尾 `-b` を除いた `asia-northeast1`。

> 注意: 静的 IP は VM に紐付いている間は無料だが、VM を削除して IP だけ残すと月 $3 程度課金される。
> 片付け時は `gcloud compute addresses delete fx-tljh-ip --region=asia-northeast1` も忘れずに。

### 5. VM `fx-tljh` を作る
| 指定 | 意味 |
|---|---|
| `--machine-type=e2-highmem-8` | 8 vCPU / 64GB RAM。50人 × メモリ上限 1GB = 50GB でもホストが溢れない |
| `--image-family=ubuntu-2204-lts` | OS は Ubuntu 22.04（TLJH の対応 OS） |
| `--boot-disk-size=128GB --boot-disk-type=pd-balanced` | 50人 × ディスク上限 2GB = 100GB を使い切っても収まる |
| `--address=<静的IP>` | 手順4で予約した IP を付ける |
| `--tags=tljh` | 手順3のファイアウォールの対象にする |
| `--metadata=fx-api-internal-ip=...,tljh-admin-users=...,tljh-user-quota-kb=...` | 04 に渡す値。VM 内から `metadata.google.internal` で読める |
| `--metadata-from-file=startup-script=04_tljh_provision.sh` | **04 の中身をそのまま渡す**。GCE が初回起動時に root で実行する |

### 6. URL と確認コマンドを表示
`http://<静的IP>` と、VM に SSH して進捗ログを見るコマンド（`journalctl -u google-startup-scripts -f`）、
完了判定（`/opt/tljh-provisioned` があれば完了）を表示して終わり。

### 再実行したとき
- VM `fx-tljh` が既に存在するとエラーで止まる。作り直すなら先に `gcloud compute instances delete fx-tljh`。
- ファイアウォールと静的 IP は既存ならスキップされるので、VM だけ作り直すのは安全。

## 04_tljh_provision.sh（VM 内で自動実行・約5〜10分）

`set -euxo pipefail` で動くので、**どこかのコマンドが失敗した時点で止まる**（中途半端な状態で完了印は付かない）。

### 1. 完了印 `/opt/tljh-provisioned` があれば即終了
startup-script は VM を再起動するたびに走る。2回目以降に TLJH を再インストールしないための仕組み。
**再プロビジョニングしたいときは、この file を消して VM を再起動する。**

### 2. メタデータから値を取得
03 が `--metadata` で渡した app 内部 IP・管理者名・クォータ値を `curl http://metadata.google.internal/...` で読む。
VM 内からしか読めない GCE の仕組み。

### 3. apt で python3 / pip / curl / quota / linux-modules-extra をインストール
`quota` は手順9のディスク上限に使うコマンド群（`quotacheck` `quotaon` `setquota`）。
`linux-modules-extra-<カーネル版>` は GCP 用 Ubuntu カーネルで分離されている追加モジュール群で、
クォータのファイル形式を扱う `quota_v2` モジュールがここに入っている。これが無いと `quotaon` が
「Quota format not supported in kernel」で失敗する（初回構築時にこれで躓いた）。

### 4. `HOME_MODE 0750` を設定
新しく作られるホームディレクトリの権限を「本人 rwx / 同グループ r-x / 他人なし」にする。
参加者 A が参加者 B の `/home/jupyter-B/` を覗いて戦略ノートブックを読めないようにするため。
Ubuntu 22.04 の既定値も 0750 だが、既定値頼みにせず明示している。

### 5. TLJH 本体をインストール
```
curl https://tljh.jupyter.org/bootstrap.py | python3 - --admin tonkou --admin kein
```
TLJH（The Littlest JupyterHub）公式のインストーラ。`/opt/tljh/` 配下に以下を入れる。
- `hub/`：JupyterHub 本体（ログイン画面・Admin パネル・ユーザーごとのサーバー起動）
- `user/`：参加者のノートブックが動く Python 環境（全員共有）
- `config/`：設定ファイル置き場

`--admin` で指定したユーザーが管理者になる。認証方式は **FirstUseAuthenticator**：
ユーザー名 + 好きなパスワードで初回ログインすると、そのパスワードがそのまま登録される。
→ **管理者 2 人は参加者より先にログインしてパスワードを確定させること**（先に他人に取られると乗っ取られる）。

ここが一番時間がかかる（数分）。

### 6. `limits.memory 1G` / `limits.cpu 1`
`tljh-config set` で書く TLJH の設定。各参加者のノートブックサーバーは **systemd の cgroup** という
Linux の仕組みで隔離されて起動するので、この値が「そのユーザーのプロセス群の上限」として OS に強制される。

| 上限 | 超えたときに起きること |
|---|---|
| メモリ 1GB | その人のカーネルだけが OOM kill される（Kernel died）。他の参加者は無傷 |
| CPU 1コア | その人が 1コア分で頭打ちになるだけ（殺されはしない）。8コアを 50人で分けるので同時に重い処理をする人が 8人を超えると全員遅くなる |

変更は `sudo tljh-config set limits.memory 2G && sudo tljh-config reload hub`。
ただし反映されるのは**その後に起動したサーバーだけ**。動作中の参加者は Admin パネルで Stop → 本人が再起動。

### 7. 全ユーザーに環境変数 `FX_API_BASE_URL` を配る
`/opt/tljh/config/jupyterhub_config.d/fx_env.py` に
```python
c.Spawner.environment = {"FX_API_BASE_URL": "http://<app内部IP>:8000"}
```
を書く。JupyterHub は各ユーザーのサーバーを起動（spawn）するときこの環境変数を渡すので、
配布ノートブック側は `os.environ.get("FX_API_BASE_URL")` で API の場所を知れる。参加者が IP を手打ちする必要がない。

### 8. 参加者用パッケージを共有環境に pip install
`/opt/tljh/user/bin/python3 -m pip install requests numpy pandas matplotlib tqdm`。
`user/` は全参加者共通の環境なので、1回入れれば全員がそのまま `import pandas` できる。

### 9. ディスククォータ（1人 2GB）
参加者が巨大ファイルをダウンロードして 128GB のディスクを埋めると全員が書き込めなくなる。それを防ぐ仕組み。

**usrquota とは**：Linux のファイルシステム（ext4）が持つ「ユーザーごとの使用量上限」機能。
ファイルシステムをマウントするときに `usrquota` オプションを付けると有効になり、
あとは `setquota` でユーザーごとの上限を書き込むと、OS がそのユーザーの書き込みを上限で止める（`Disk quota exceeded` エラー）。

スクリプトがやっていること：
1. `/etc/fstab`（起動時にどのディスクをどう mount するかの設定 file）のルート `/` の行に `usrquota` を追記
2. `mount -o remount /` で再起動せずにオプションを反映
3. `quotacheck -um /` で現在の使用量を集計して管理 file（`/aquota.user`）を作る
4. `quotaon /` でクォータを有効化
5. `quotaon -p /` で「user quota on / is on」になっていることを確認（なっていなければスクリプトはここで失敗する）
6. **cron（毎分実行）** で `jupyter-*` という名前の全ユーザーに `setquota ... 2GB` を適用

> fstab の列区切りは**タブ**。sed で options 列に `usrquota` を足すとき `[^ ]*` と書くとタブを越えて
> 隣の dump 列に付いてしまい（`0,usrquota`）クォータが効かなくなる。`[^[:space:]]*` にしてある。

なぜ cron か：TLJH は参加者が初回ログインしたときに Linux ユーザー `jupyter-<名前>` を**動的に作る**。
作成時点でクォータを設定するフックが TLJH にないので、毎分「全 jupyter- ユーザーに上限を設定し直す」ことで
新規ユーザーにも最大 1 分以内に上限が効くようにしている（`setquota` は既に設定済みのユーザーに何度かけても無害）。

> `usrquota` が効くのはルート FS（`/home` を含む）。`/dev/shm`（メモリ上の tmpfs）は対象外だが、
> それはメモリなので手順6の 1GB 上限で抑えられる。

### 10. `tljh-config reload` → 完了印を作る
設定を JupyterHub に読み込ませ、`/opt/tljh-provisioned` を作って終了。

## 完了後にできること・確認すること

- `http://<静的IP>` にアクセス → 管理者名 + 任意のパスワードでログイン（そのパスワードが登録される）
- Admin パネル（`/hub/admin`）：ユーザー追加/削除、各ユーザーのサーバー Start/Stop。**暴走ユーザーはここで Stop**
- Admin パネルから CPU/メモリ上限は変えられない（手順6の `tljh-config` のみ）
- リハーサルでの確認項目は `infra-setup/README.md` と `05_verify.sh` を参照

## 用語ミニ辞書

| 用語 | 意味 |
|---|---|
| startup-script | GCE が VM 起動時に root で自動実行するスクリプト。メタデータとして VM に渡す |
| メタデータ | GCE が VM に紐付けて持つ key=value。VM 内から `metadata.google.internal` で読める |
| 静的 IP / エフェメラル IP | 予約して固定した外部 IP / 起動のたびに変わる外部 IP |
| 冪等（べきとう） | 何度実行しても結果が同じ。「既にあればスキップ」の処理がそれ |
| cgroup | Linux のプロセスグループ単位でのリソース上限機能。TLJH はユーザーごとにこれを使う |
| OOM kill | メモリ上限を超えたプロセスを OS が強制終了すること |
| usrquota | ext4 のユーザーごとディスク使用量上限機能 |
| cron | 決まった時刻・間隔でコマンドを実行する Linux の仕組み。`/etc/cron.d/` に設定を置く |
| TLJH | The Littlest JupyterHub。1台の VM で数十人向け JupyterHub を立てるための配布物 |
| Spawner | JupyterHub がユーザーごとのノートブックサーバーを起動する部品。環境変数や上限はここに設定する |
