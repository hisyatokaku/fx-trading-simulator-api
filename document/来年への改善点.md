# 来年への改善点（2026-09 イベントの振り返り）

最終更新: 2026-09-11。細かい所見・文言修正・リハーサル時の気づきは `document/その他の改善メモ.md` に分けている。

優先度は「参加者の体験・公平性に直結するか」「当日に止まるリスクか」で 3 段階。

## 高（次回の実施前に必ずやる）

### 1. リポジトリを private にする

**現状の問題**
- フォークは単独で private にできない。`data/scenarios.csv` に EVAL の日付、`data/rates.csv` に当日のレートが入っており、GitHub を見れば答えが取れる。
- 一度 public だった履歴はクローンやキャッシュに残り得るので、private 化は「今後の露出を減らす」対策。過去分の取り消しにはならない。

**手順（自分で完結する方法）**
1. 現フォークを `fx-trading-simulator-api-fork` などに改名する
2. 元の名前で private リポジトリを新規作成する
3. ローカルから `git push --mirror` で全ブランチ・タグを移す
4. GitHub Actions のシークレット（GCP 認証）を新リポジトリに再登録する
5. 未マージ PR を再作成する（PR と Issue の履歴は移らない）
6. ローカルの `git remote set-url`、WebUI リポジトリの README リンク、運営手順の URL を更新する
7. 古いフォークを削除する（archive では public のまま残る）

**注意**
- private では Actions の無料枠が月 2,000 分。deploy は e2e のタイムアウト待ちで毎回 5 分以上使うので、項目 15 を先にやる
- 上流へ PR を戻す予定が無いことを確認しておく
- 別案: GitHub サポートに「Detach fork」を依頼すれば PR 履歴ごと残せるが、数日かかる

### 2. EVAL の日付とレートをリポジトリに置かない
- 1 をやっても履歴に残るので、置き場所そのものを変える。本番用データは評価開始の直前に手動で DB 投入する「秘密シナリオ方式」が実装変更なしで済む。seed は upsert なので消されない。

### 3. EVAL の未完走セッションで答えを読める抜け道を塞ぐ
- サーバは「完走したセッションがあれば 409」としか見ない。チーム ID で EVAL を開始し、最後の 1 tick 手前まで進めれば `next` の応答から当日のレートを全部読めて、その後に正規の提出ができる。
- 対処: EVAL は未完走を含めて 1 チームあたり開始 2 回までに制限する（事故のやり直し余地は残す）。

### 4. app/DB のディスク拡張
- 30 GB のディスクがイベント中に使用率 90%（空き 2.9 GB）まで逼迫した。balances は 1 日シナリオ 1 本で 2〜3 MB 増える。
- 対処: 事前に 100 GB 程度へ拡張（VM 停止なしで可能。`disks resize` → `growpart` → `resize2fs`）。リハーサル分の balances を掃除する手順も入れる。

### 5. `fetch_rates_to_jpy` / `fetch_rates_for_last_n_ticks` が EVAL で黙って空を返す

**何が起きたか**
- 2 関数は `GET /api/rate/{timestamp}` を使う。サーバは EVAL 期間の時刻を 403 で拒否する（事前に答えを読めないようにする仕様）。
- 関数は 200 以外をすべて `{}` にして返し、エラーも警告も出さない。
- あるチームが「戦略の初期レート（過去 n tick）」をこの関数で取る実装のまま本番提出した。TEST では正常に動いていたが、EVAL では履歴が空のまま走り、戦略が想定どおり働かないまま 1 回限りの提出が確定した。
- 教材にこの制約が書かれておらず、docstring も「無い場合は空」としか書いていない。

**対処案（組み合わせる）**
1. 教材に明記: 該当関数の docstring と「本番提出」の説明に「EVAL 期間では 403 になり空を返す。本番で使えるレートは `next` の応答だけ」と書く
2. 関数側で 403 を区別してメッセージを表示する
3. 解答例を「開始前レートに依存しない」形にする（最初の n tick は観測に使い、それから取引する）
4. 運営ルールとして、この事故を「再提出を認める」対象にするか事前に決めておく（認めるなら該当チームの完走セッション削除が必要）

**根本的な選択肢**
- 「開始前の履歴は見られない」こと自体を教材の前提に組み込む（推奨）
- あるいは、セッション開始時にサーバが直前 n tick 分のレートを応答に含める設計にする。参加者が事前取得 API を叩く必要が無くなる

### 6. main へのマージで app が再起動し、実行中セッションが切れる
- deploy ワークフローは main へのマージのたびに `docker compose up -d app` で app を入れ替える。ドキュメントだけの変更でも再起動し、その瞬間の全参加者の実行が ConnectionAbortedError で止まる（今回発生）。
- 対処: deploy.yml に `paths-ignore`（document/**、*.md、infra-setup/**）を足す。加えてイベント中は main へのマージを凍結する運用にする。

## 中（やると当日の手戻りが減る）

### 7. 提出前にシナリオ名 5 件の存在確認を入れる
- `eval_submission` の「5 件でなければ拒否」と「1 回提出」の組み合わせで、途中失敗（3 件目でシナリオ名の打ち間違い）からの復旧手順が無く、運営が案内する形になった。
- 対処: 確認プロンプトの前に `GET /api/scenario/{name}` で 5 件を照合し、1 件でも無ければ何も始めない。

### 8. EVAL 判定を大文字小文字によらず行う
- `"EVAL" in tc` は大文字のみ一致。小文字で打つと 5 件チェックも確認プロンプトも通らず、大文字の打ち間違いだけが提出を消費する非対称がある。`tc.upper()` にする。

### 9. EVAL→TEST の付け替え時は旧行を DB から消す
- #59 で EVAL5〜13 を TEST4〜18 に改名したが、seed は削除をしないため旧 EVAL 行が同じ日付で DB に残った。`/api/rate/{timestamp}` の EVAL 判定が旧行に当たり、TEST4〜18 の期間でも 403 になった。
- 対処: seed に「CSV に無い行の削除」を持たせるか、付け替え手順に旧行（と紐づくセッション）の削除を入れる。

### 10. app の自動起動
- VM 再起動後に docker compose を手で上げる運用。compose に `restart: unless-stopped` を付けるだけで解消する。

### 11. 提出締切の扱いを事前に決めて周知する
- 締切 14:40 を過ぎて開始したチームが 10 中 5。無効・減点・許容のどれにするかを事前に決め、集計スクリプトの `first_submit` で機械的に判定できるようにする。

### 12. 集計・順位表スクリプトをリポジトリに入れる
- 今回は DB から CSV を手で落として pandas で集計した。チーム × シナリオの内訳、中央値、順位、最初の提出時刻を出すスクリプトを `scripts/` に置く（今回のコードで足りる）。

### 13. day1 で Day2 の訓練データを見せない
- day1.ipynb は Part 1 で `TEST0`、発展課題 C で `TEST1` を使う。TEST0〜18 は Day2 の訓練シナリオなので、Day1 の時点で参加者が Day2 のレート系列を見て戦略を作り込める。
- 対処案: day1 の実データ例を TUTORIAL か Day2 で使わない専用シナリオに差し替える／発展課題 C の言及を外す／許容するなら Day2 で「TEST は練習用」と明示する。

### 14. day2 の結果確認の文言をチーム ID に
- チーム提出（group-N）に変えたのに、結果確認の案内は「自分の user_id を入力」のまま。

### 15. e2e テストのタイムアウト修正
- デプロイ後の `test-deployment` が毎回 5 分でタイムアウト（TEST0 の 1,439 tick を GitHub Actions から回すため）。デプロイ自体には無影響だが、private 化すると Actions の枠を無駄に使う。短いシナリオ（DEMO_5MIN）に変えるか timeout を延ばす。

### 16. 表彰方式と初期資産を早めに決める
- 個人かチームか、中央値か順位点か、初期資産 100 万か 1 億か、が今回も直前まで未決だった。教材の数値記載と合格ラインに影響するため、教材改修の前に決める。
